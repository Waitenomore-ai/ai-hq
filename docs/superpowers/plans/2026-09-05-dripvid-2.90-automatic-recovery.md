# DripVid 2.90 Automatic Recovery Implementation Plan

> **For agentic workers:** Execute this plan task-by-task with TDD and review checkpoints. Use an isolated worktree/feature branch for implementation. Automated tests must never restart real production services.

**Goal:** Allow AI HQ to detect persistent DripVid outages, diagnose a fixed set of components, perform tightly bounded automatic recovery through the existing Tool Gateway/Host Helper security boundary, verify the result, and escalate safely when recovery is not appropriate or does not work.

**Architecture:** Add a separate `service.recover` capability plus a persisted DripVid recovery coordinator. The observer reads DripVid's trusted readiness endpoint and existing read-only operational tools. When policy says a mutation is justified, it creates a BLUE-risk single-step mission which must execute through `MissionExecutor -> ToolGateway -> SafetyService -> scoped approval rule -> ServiceRecoverAdapter -> Host Helper`. Normal `service.restart`, deploy, and rollback approval rules remain unchanged.

**Tech stack:** Python 3.12+, SQLAlchemy, Alembic, FastAPI project infrastructure, httpx, pytest, Ruff, systemd Host Helper.

**Design:** `docs/superpowers/specs/2026-09-05-dripvid-2.90-automatic-recovery-design.md`

**Dependency:** DripVid plan `Waitenomore-ai/dripvid/docs/superpowers/plans/2026-09-05-dripvid-2.90-health-contract.md` must be merged/deployed before production recovery is enabled. AI HQ implementation may be developed and tested before that using fakes.

## Non-negotiable safety rules

- No arbitrary shell command, executable, host, path, URL, systemd unit, or journal unit may come from a mission.
- `service.recover` is distinct from `service.restart`.
- `service.restart`, `deployment.deploy`, and `deployment.rollback` retain their existing approval requirements.
- Real recovery requires exact `service.recover` permission and an exact active scoped approval rule.
- FREEZE blocks recovery.
- SAFE blocks real mutation.
- Simulation produces zero real mutation.
- Media storage unavailable/unwritable is never “fixed” by restarting services.
- PostgreSQL is restarted only when its systemd service is explicitly inactive/failed; a running-but-unhealthy database is escalated instead.
- Recovery budgets count **real** attempts only.
- The worker never directly invokes Host Helper or subprocess for a recovery mutation.
- Recovery remains disabled by default in configuration.

## Fixed recovery component contract

Mission-visible component keys are fixed:

| Component | Trusted system service | Auto-recovery policy |
|---|---|---|
| `app` | `dripvid.service` | recover when inactive/failed after threshold |
| `mcp` | `dripvid-mcp.service` | recover when inactive/failed after threshold |
| `proxy` | `nginx.service` | recover when inactive/failed after threshold |
| `tunnel` | `cloudflared.service` | recover when inactive/failed after threshold |
| `database` | `postgresql.service` | recover only when service itself is inactive/failed |

The mapping exists only in trusted server-side code. Missions never receive or submit the service-unit strings.

## Default policy values

- observation interval: 30 seconds;
- persistent failure threshold: 3 consecutive failed observations;
- cooldown: 300 seconds;
- real recovery budget: 2 attempts per component in rolling 3600 seconds;
- post-recovery verification window: 60 seconds;
- recovery disabled by default;
- observe-only mode enabled by default.

**Files:**

### Why this task exists

`SafetyService.evaluate()` already returns `scoped_rule_id`, and `ApprovalService.consume_rule()` already increments an execution count, but Tool Gateway must guarantee that a real scoped mutation consumes the authorizing rule before adapter mutation. Otherwise a `max_execution_count` would not enforce an actual recovery ceiling.

### Red

Tests must prove:

1. BLUE mutating request with exact scoped rule executes and increments `execution_count` once;
2. exhausted scoped rule causes no adapter mutation;
3. expired rule causes no mutation;
4. simulation causes no scoped-rule consumption and no adapter mutation;
5. ordinary approved `service.restart` behavior is unchanged;
6. a scoped rule for `service.recover`, target `dripvid`, component `app` conditions cannot authorize component `proxy`;
7. two concurrent execution attempts cannot both consume the final allowed use.

### Implementation

Before real adapter execution, if `safety.scoped_rule_id` is present and the request mutates external state, atomically consume the rule. A failed consume becomes a blocked/failed no-mutation outcome.

Do not consume after the adapter, because that permits mutation before authorization accounting.
