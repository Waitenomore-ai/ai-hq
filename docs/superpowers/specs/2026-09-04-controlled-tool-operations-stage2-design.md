# AI HQ Stage 2: Controlled Real-World Tool Gateway Operations

Date: 2026-09-04
Status: Approved design
Depends on: Autonomous Missions Stage 1
Baseline commit: da693a716ff499b31dec5c30e828a7a0c81f4377

## 1. Purpose

Stage 2 gives AI HQ controlled access to genuine operational
capabilities while preserving the Tool Gateway as the mandatory
security boundary.

The objective is not general shell access.

The objective is a small, explicit set of registered operational
capabilities whose permissions, targets, safety policy, approvals,
execution, and results can be inspected and audited.

The execution path remains:

Mission
-> Tool Gateway
-> exact capability permission
-> safety decision
-> approval when required
-> registered restricted adapter
-> real operation
-> operations ledger

No mission, agent, planner, API endpoint, or worker may bypass this
path for Stage 2 operations.

## 2. Security Boundary

The Tool Gateway remains the only execution boundary for autonomous
mission tools.

Stage 2 MUST NOT provide:

- arbitrary agent-supplied shell commands;
- arbitrary executable paths;
- arbitrary systemd unit names;
- arbitrary filesystem operations;
- arbitrary hostnames or network targets;
- direct subprocess execution from the mission layer;
- direct host-helper execution from the mission layer;
- direct adapter invocation from missions;
- approval bypasses;
- permission wildcards;
- implicit fallback from an unknown capability to a general command.

Unknown capabilities and unknown targets fail closed.

A registered capability must map to a specific adapter operation.

## 3. Initial Capability Set

Stage 2 begins with a deliberately small operational surface.

### 3.1 Read-only capabilities

The initial read-only capabilities are:

- `system.health.read`
- `service.status.read`
- `service.logs.read`

These operations may execute without a human approval only when:

1. the requesting agent has the exact capability permission;
2. the target is registered for that capability;
3. the safety service allows the request; and
4. the adapter validates all arguments.

Read-only operations must not mutate service or host state.

### 3.2 Mutating capabilities

The initial mutating capability is:

- `service.restart`

A service restart MUST require an approval decision before real
execution.

Approval applies to the exact canonical request fingerprint already
used by the Tool Gateway approval system. Approval for one service,
target, mission, or action must not authorize a different operation.

### 3.3 Deployment capabilities

The architecture reserves these explicit capability names:

- `deployment.deploy`
- `deployment.rollback`

They are controlled operations, not arbitrary command wrappers.

Deployment and rollback MUST require approval before real execution.

Their implementation may be introduced after the core read/restart
boundary is proven, but their contracts and security requirements are
part of Stage 2.

## 4. Registered Targets

Stage 2 initially recognizes these logical targets:

- `ai-hq`
- `dripvid`

Logical targets are resolved by trusted server-side configuration.

An agent supplies the logical target name only.

The agent must not be able to replace that logical target with:

- a hostname;
- an IP address;
- a filesystem path;
- a systemd unit;
- a shell fragment;
- a deployment directory; or
- another infrastructure identifier.

Target configuration determines the concrete service/unit information
used by an adapter.

Target configuration is trusted operator configuration and is not
generated by a mission.

## 5. Adapter Architecture

Stage 2 introduces or extends restricted operational adapters behind
the existing Tool Gateway registry.

Adapters have one responsibility: execute a narrowly defined,
validated capability against a registered target.

Adapters MUST validate inputs again at the execution boundary.

An adapter must reject arguments outside its contract.

No adapter may interpret an arbitrary string from a mission as a
shell command.

Where an operating-system command is required internally, the adapter
must construct the invocation from trusted constants and validated
allowlisted values.

Shell interpolation is prohibited.

Execution must use argument-vector semantics rather than
`shell=True`.

## 6. System Health

`system.health.read` returns bounded diagnostic information for a
registered target.

The result may include data such as:

- target identity;
- service availability;
- configured health endpoint result;
- basic runtime state;
- bounded resource/health information explicitly configured for the
  target.

The capability is diagnostic only.

It must not expose secrets, environment dumps, credentials, tokens,
or unrestricted process information.

## 7. Service Status

`service.status.read` returns bounded status information for the
registered service associated with the logical target.

The service identifier comes from trusted target configuration.

The mission cannot select an arbitrary service.

The response should be structured and bounded so autonomous missions
can reason about it without parsing unrestricted terminal output.

## 8. Service Logs

`service.logs.read` provides bounded recent logs for a registered
target.

Requirements:

- read-only;
- bounded maximum number of records/lines;
- bounded maximum response size;
- no arbitrary journal unit selection;
- no arbitrary file path;
- secrets should be redacted where practical;
- arguments such as requested line count must have strict limits.

The target configuration selects the permitted log source.

## 9. Service Restart

`service.restart` performs a restart only for the service mapped to
the registered logical target.

Requirements:

- exact capability permission;
- registered target;
- safety evaluation;
- mandatory approval before mutation;
- exact approval fingerprint;
- restricted adapter;
- result recorded in the operations ledger.

The adapter constructs the restart operation from trusted target
configuration.

A mission cannot supply a service/unit name.

After restart, the adapter should return a structured result and,
where configured, a bounded post-restart status/health observation.

Failure to restart or failure of post-restart validation must be
reported explicitly.

## 10. Deploy and Rollback

`deployment.deploy` and `deployment.rollback` are explicit workflows,
not general shell execution.

Both require human approval.

A deployment adapter may invoke only a trusted, operator-configured
deployment entry point for the registered target.

A mission may request deployment intent and validated deployment
parameters, but may not provide the command that implements it.

Rollback must use a trusted release mechanism and validated release
identifier.

Arbitrary filesystem paths are prohibited.

Deployment and rollback results must be structured and auditable.

## 11. Simulation

The existing Tool Gateway simulation decision remains supported.

When safety policy selects simulation:

- the real adapter must not mutate the external system;
- the outcome is recorded as simulated;
- the mission receives a structured simulated outcome;
- no command with external side effects is executed.

Simulation must remain distinguishable from successful real execution.

## 12. Permissions

Permissions remain exact capability permissions.

Possessing:

`service.status.read`

does not imply:

`service.restart`

Possessing:

`service.restart`

does not imply:

`deployment.deploy`

No Stage 2 capability uses wildcard permission matching.

The existing Tool Gateway permission check remains authoritative.

## 13. Safety and Approval

The existing Safety Service and Approval Service remain authoritative.

Read-only operations can execute only when safety policy permits them.

Mutating operations are marked as external-state mutations and are
configured so the safety decision requires approval.

The mission executor does not turn an approval into direct execution.

After approval, the request returns through the Tool Gateway and is
re-evaluated against the exact persisted request.

Rejected, expired, missing, or mismatched approval fails closed.

## 14. Audit and Operations Ledger

Stage 2 must preserve a useful audit trail.

For real operational requests, the existing operations ledger should
make it possible to reconstruct:

- mission identifier;
- requesting agent;
- capability;
- logical target;
- safety/permission outcome;
- approval requirement and decision where applicable;
- execution attempt;
- structured result or failure;
- whether the outcome was simulated or real.

Secrets and credentials must not be written into the ledger.

Stage 2 implementation must review the existing ledger events and add
events only where the current boundary does not provide enough
information to reconstruct this sequence.

## 15. Failure Behaviour

Stage 2 fails closed.

Examples:

- unknown capability -> blocked;
- unknown target -> blocked;
- missing exact permission -> blocked;
- invalid arguments -> blocked/failed without operation;
- required approval missing -> waiting for approval;
- approval rejected/expired/mismatched -> no mutation;
- adapter execution failure -> failed outcome;
- post-operation validation failure -> explicit failed result;
- malformed configuration -> capability unavailable.

A failed operation must not silently retry a mutation.

Retry policy, if later introduced, must distinguish safe reads from
mutations and must have explicit idempotency rules.

## 16. Autonomous Mission Integration

Stage 1 autonomous missions remain consumers of the Tool Gateway.

A mission step references a registered Stage 2 capability and logical
target.

The mission executor does not gain host privileges.

For approval-required steps:

1. the mission reaches the step;
2. Tool Gateway returns `WAITING_APPROVAL`;
3. mission and step persist their waiting state;
4. approval is decided through the existing approval system;
5. resume re-submits the persisted exact request to Tool Gateway;
6. Tool Gateway re-evaluates safety/approval;
7. only then may the restricted adapter perform the operation.

Completed steps must not be re-executed after worker/process restart.

## 17. Configuration

Real operational target configuration must be server-controlled.

Configuration should describe only the information adapters need, for
example:

- logical target key;
- allowed capability set;
- service/unit identifier;
- health endpoint or bounded health strategy;
- log source;
- trusted deploy entry point where enabled;
- trusted rollback mechanism where enabled.

Configuration validation occurs at startup or registry construction.

Invalid targets should not be registered.

Secrets should use the project's existing secret/configuration
mechanism rather than mission arguments.

## 18. API Boundary

Stage 2 does not create a generic command-execution API.

Any API exposure for operational tools must create or drive the same
Tool Gateway request path used by missions.

Authentication and authorization remain required.

API callers cannot directly invoke adapters.

Approval-required operations must expose their waiting state rather
than performing the mutation immediately.

## 19. Concurrency and Idempotency

Read-only operations may safely be repeated within normal operational
limits.

Mutations require stronger guarantees.

At minimum:

- a completed mission step is never intentionally re-executed;
- an approval resume uses the persisted request;
- concurrent workers must not independently execute the same mutating
  mission step;
- adapters must not implement hidden automatic retries for mutations.

The Stage 2 implementation must inspect the Stage 1 step-claim
mechanism and harden it if it does not prevent concurrent execution.

## 20. Testing Requirements

Stage 2 requires automated tests for:

- exact capability permission enforcement;
- unknown capability rejection;
- unknown target rejection;
- target-to-service allowlisting;
- argument validation;
- read-only health execution;
- read-only status execution;
- bounded log retrieval;
- log argument limits;
- mandatory approval for restart;
- approval fingerprint mismatch rejection;
- simulation causing no external mutation;
- restart invoking only the configured service;
- adapter failures becoming structured failures;
- mission pause/resume through approval;
- completed steps not executing twice;
- concurrent mutation claim protection;
- operations ledger coverage;
- no direct mission-to-host execution;
- no shell interpolation/general command execution.

Tests for real command adapters must use fakes/mocks/test doubles.
The automated test suite must not restart production services or
perform real deployments.

## 21. Implementation Order

Implementation should proceed in this order:

1. inspect and document existing Stage 1 concurrency/audit boundaries;
2. define trusted target configuration contracts;
3. implement target registry and validation;
4. implement bounded read-only operational adapters;
5. integrate adapters with Tool Gateway registry;
6. enforce capability/target argument contracts;
7. implement approval-required service restart;
8. verify simulation produces no mutation;
9. harden autonomous mission step claiming/idempotency if required;
10. verify/add audit coverage;
11. integrate autonomous worker execution where appropriate;
12. expose bounded operational state through existing authenticated
    interfaces where required;
13. implement trusted deploy/rollback adapters only after the core
    operational boundary passes its safety tests;
14. run targeted security tests and full regression.

## 22. Stage 2 Acceptance Criteria

Stage 2 is complete only when all of the following are true:

- AI HQ can perform configured read-only operational checks through
  Tool Gateway.
- AI HQ can request a restart of a registered service.
- A real restart cannot occur without required approval.
- Missions cannot select arbitrary services or hosts.
- Missions cannot submit arbitrary shell commands.
- Unknown capabilities and targets fail closed.
- Simulation cannot cause external mutation.
- Operational results are structured.
- Relevant decisions and outcomes are auditable.
- Autonomous missions remain behind Tool Gateway.
- Concurrent workers cannot execute the same mutating step twice.
- Restart behaviour is covered with test doubles rather than
  production mutations.
- Deployment and rollback, if enabled, use trusted configured entry
  points and mandatory approval.
- Full regression tests pass.
- No production service is modified merely by running the test suite.

## 23. Explicit Non-Goals

Stage 2 does not include:

- unrestricted SSH;
- unrestricted shell access;
- arbitrary command execution;
- arbitrary filesystem management;
- arbitrary package installation;
- arbitrary systemd management;
- arbitrary network scanning;
- bypassing Tool Gateway;
- automatic approval of high-impact operations;
- the final AI HQ control dashboard.

The full control dashboard remains Stage 3.
