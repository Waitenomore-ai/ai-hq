# DripVid 2.90: Automatic Recovery Through AI HQ

Date: 2026-09-05
Status: Approved design
Depends on: AI HQ Stage 2 Controlled Real-World Tool Gateway Operations
Primary repositories: `Waitenomore-ai/ai-hq`, `Waitenomore-ai/dripvid`

## 1. Purpose

DripVid 2.90 should recover automatically from a small set of common service failures without weakening AI HQ's existing Tool Gateway, Safety Service, Approval Service, simulation, audit, or host-execution boundaries.

The goal is not general self-healing infrastructure and not unrestricted autonomous administration.

The goal is a narrowly scoped DripVid recovery loop that:

1. detects a persistent failure;
2. confirms the affected component;
3. captures bounded diagnostics before mutation;
4. performs at most one allowlisted recovery action at a time;
5. verifies that recovery restored health;
6. records the complete decision and result; and
7. stops and escalates instead of entering a restart loop.

Existing manual `service.restart`, `deployment.deploy`, and `deployment.rollback` operations keep their current approval requirements.

## 2. Existing Baseline

DripVid already provides the operational signals needed for this project:

- `/health/live` for process liveness;
- `/health/ready` and `/health` for dependency-aware readiness;
- dependency probes for PostgreSQL, Jellyfin, Radarr, Sonarr, qBittorrent, and request-sync health;
- core-storage availability, writability, capacity, and reserve checks;
- admin storage notifications;
- bug reports that already capture page path and browser user agent.

AI HQ already provides the security and execution foundation:

- trusted logical operational targets;
- `system.health.read`;
- `service.status.read`;
- `service.logs.read`;
- approval-protected `service.restart`;
- Tool Gateway exact-capability permissions;
- Safety Service decisions;
- scoped approval rules;
- simulation mode;
- Host Helper restricted execution;
- operations ledger auditing;
- autonomous missions executed through MissionExecutor -> Tool Gateway -> Host Helper.

This project extends those existing boundaries. It must not create a second privileged path.

## 3. Design Summary

Introduce a separate capability:

`service.recover`

`service.recover` is not an alias for `service.restart` and does not make ordinary restarts approval-free.

It is a recovery-only mutation whose execution is permitted only when all of these are true:

- the target is the trusted logical target `dripvid`;
- the requested component is a server-configured recovery component key;
- the requesting agent has the exact `service.recover` capability;
- the recovery mission is classified as BLUE risk;
- an active scoped approval rule exactly authorizes automatic recovery for that component and condition set;
- AI HQ is not in FREEZE mode;
- AI HQ is not in SAFE mode for real mutations;
- simulation mode is respected;
- the failure threshold has been met;
- the component recovery policy permits mutation for the observed failure state;
- the component is outside its cooldown period;
- its restart/recovery budget has not been exhausted; and
- no other recovery action is already in progress for the same component.

The normal `service.restart` capability remains unchanged and continues to require a per-request approval.

## 4. Recovery Components

Missions and agents must never submit raw systemd unit names.

The DripVid recovery profile exposes only these logical component keys:

- `app`
- `mcp`
- `proxy`
- `tunnel`
- `database`

Trusted server-side configuration maps those keys to concrete services.

Initial production mapping:

- `app` -> `dripvid.service`
- `mcp` -> `dripvid-mcp.service`
- `proxy` -> `nginx.service`
- `tunnel` -> `cloudflared.service`
- `database` -> `postgresql.service`

No mission-controlled service name, executable, path, host, port, command fragment, or shell expression may be accepted.

Unknown component keys fail closed.

## 5. Component Recovery Policy

### 5.1 App

The `app` component is eligible for automatic recovery when DripVid readiness repeatedly fails and service status confirms the application service is inactive, failed, or otherwise not operational.

The recovery action is one restart of the trusted DripVid service.

After restart, AI HQ must verify both service status and DripVid readiness before reporting recovery success.

If the service is active but readiness is failing only because another dependency is unhealthy, AI HQ must identify the failing dependency and must not blindly restart DripVid unless the policy explicitly identifies the app process as the failed component.

### 5.2 MCP

The `mcp` component is eligible for automatic recovery when the trusted DripVid MCP service is inactive or failed.

The recovery action is one restart of the trusted MCP service followed by a bounded service-status check and any configured MCP health check.

### 5.3 Proxy

The `proxy` component is eligible for automatic recovery when the trusted Nginx service is inactive or failed.

The recovery action is one restart of the trusted Nginx service followed by service-status verification and a bounded local DripVid HTTP probe.

Configuration or syntax failures must not produce repeated restart attempts. A failed post-restart validation ends automatic recovery for that incident and escalates.

### 5.4 Tunnel

The `tunnel` component is eligible for automatic recovery when the trusted Cloudflared service is inactive or failed.

The recovery action is one restart of the trusted Cloudflared service followed by service-status verification.

A public reachability failure while Cloudflared remains active must be diagnosed before mutation; the recovery loop must not assume every external connectivity problem is a tunnel-process failure.

### 5.5 Database

PostgreSQL receives a stricter policy.

Automatic recovery is permitted only when system service status explicitly reports PostgreSQL as inactive or failed.

If PostgreSQL is active but DripVid's database probe fails, AI HQ must collect bounded diagnostics and escalate without repeatedly restarting PostgreSQL.

This prevents automatic recovery from turning query, authentication, schema, lock, connection-pool, or storage problems into unnecessary database restarts.

## 6. Storage Is Not a Restart Problem

Missing, unavailable, read-only, or incorrectly mounted DripVid media storage is never repaired by restarting DripVid services.

When DripVid core-storage checks report unavailable or not writable:

- record a critical storage incident;
- do not invoke `service.recover` for app, database, proxy, or tunnel merely because playback or requests are failing as a consequence;
- preserve the existing fail-closed storage policy for media operations; and
- escalate to the operator with the observed storage status.

Low free space remains a warning/operational condition rather than an automatic restart trigger.

## 7. Failure Confirmation

A single failed health observation must never trigger a mutation.

Default policy:

- observe every 30 seconds;
- require 3 consecutive qualifying failures before opening an automatic recovery incident;
- reset the consecutive-failure count after a confirmed healthy observation.

A qualifying failure means a health/status result that maps to a configured recovery condition. Transient HTTP failures, timeouts, or one-off dependency errors are recorded but do not immediately mutate the host.

These values are trusted operator configuration and are not mission arguments.

## 8. Diagnostics Before Mutation

Before any automatic recovery mutation, AI HQ must collect a bounded diagnostic snapshot using existing read-only capabilities.

The snapshot should include, where applicable:

- DripVid readiness result;
- component service status;
- recent bounded service logs;
- storage availability/writability status;
- current recovery counters/cooldown state;
- incident timestamps; and
- identified failing dependency/component.

Diagnostics must not include environment dumps, credentials, access tokens, unrestricted process listings, or arbitrary journal/file access.

The diagnostic result becomes part of the incident audit trail.

## 9. Cooldown and Recovery Budget

Automatic recovery must stop before it becomes a restart loop.

Default policy per component:

- minimum 10-minute cooldown after a real recovery attempt;
- maximum 2 real recovery attempts in any rolling 60-minute window;
- only 1 in-flight recovery action per component;
- a failed post-recovery health check counts against the budget;
- simulated recoveries do not count as real mutations but are recorded separately.

When the budget is exhausted, the component enters `escalated` state for the incident and no further automatic mutation occurs until the budget window clears or an operator explicitly resolves/resets the incident.

Recovery limits must be persisted so a worker or process restart cannot reset the protection.

## 10. Scoped Pre-Authorization

AI HQ already supports scoped approval rules. Automatic recovery must use that mechanism rather than adding a general approval bypass.

`service.recover` should be a BLUE-risk mutating action.

Production enablement creates explicit scoped approval rules for the exact trusted target/component condition sets that the operator wants AI HQ to self-heal.

Example conceptual scope:

- action: `service.recover`
- target: `dripvid`
- risk: `BLUE`
- conditions: exact recovery component + automatic-recovery policy marker
- expiry: finite and operator-controlled
- execution limit: optional additional ceiling

A missing, expired, exhausted, or condition-mismatched scoped rule means no automatic mutation.

The code must not silently create its own scoped approval rule. Production activation is an operator action.

## 11. Safety and Operating Modes

Existing Safety Service behavior remains authoritative.

Automatic recovery must obey:

- FREEZE -> block all recovery mutations;
- SAFE -> block external-state mutations;
- simulation mode -> return simulated recovery without invoking the transport;
- RED risk -> blocked;
- missing exact capability permission -> blocked;
- missing matching scoped rule -> approval required / no autonomous mutation.

No recovery subsystem may call the adapter or Host Helper directly to avoid these decisions.

## 12. Recovery Execution Path

The only permitted real execution path is:

Health observer
-> recovery incident evaluator
-> persisted recovery mission/step
-> MissionExecutor
-> Tool Gateway
-> exact `service.recover` permission
-> Safety Service
-> matching scoped approval rule
-> `ServiceRecoverAdapter`
-> trusted recovery component mapping
-> Host Helper
-> fixed system operation
-> post-recovery verification
-> Operations Ledger / recovery incident record

The observer/evaluator may decide that recovery is warranted, but it never receives host privileges.

## 13. Adapter Contract

Add a dedicated `ServiceRecoverAdapter` rather than weakening `ServiceRestartAdapter`.

The adapter contract accepts only:

- capability `service.recover`;
- target `dripvid`;
- one parameter: `component`;
- a component key present in trusted recovery configuration; and
- `mutates_external_state=True` for real execution.

Any additional parameter fails validation.

The adapter resolves the logical component to trusted configuration before transport execution.

The mission cannot supply a unit name.

## 14. Trusted Recovery Configuration

Recovery configuration is server-controlled and validated at startup.

The configuration model should contain, at minimum:

- logical target key;
- component key;
- concrete trusted service unit;
- optional trusted log unit;
- optional trusted health URL/strategy;
- whether automatic recovery is enabled;
- allowed qualifying states;
- whether restart while active-but-unhealthy is permitted;
- confirmation threshold;
- observation interval;
- cooldown duration;
- rolling budget size/window; and
- post-recovery verification strategy.

Invalid configuration must disable the affected recovery component rather than falling back to arbitrary values.

No secrets belong in mission parameters or ledger metadata.

## 15. Persistence Model

Automatic recovery needs persisted incident/counter state so safety protections survive process restarts.

Persist enough information to reconstruct:

- incident identifier;
- target;
- component;
- first failure time;
- last failure time;
- consecutive failure count;
- incident state (`observing`, `diagnosing`, `recovering`, `healthy`, `escalated`);
- last recovery attempt time;
- rolling real recovery attempts;
- latest pre-recovery diagnostic summary;
- latest post-recovery verification summary; and
- linked mission/tool outcome identifiers where available.

Persistence must not store raw secrets or unbounded log output.

## 16. Concurrency

Two workers must never recover the same component concurrently.

The recovery subsystem must use a database-backed conditional claim/transition before creating or executing a recovery mutation.

The existing atomic autonomous mission-step claiming remains required after the recovery incident is converted to a mission step.

An in-progress incident must not spawn duplicate mutating missions on every observer tick.

## 17. Post-Recovery Verification

A successful systemd restart is not enough to mark an incident resolved.

After a real recovery action:

1. wait only for a bounded configured settling period;
2. read service status;
3. run the configured health/readiness probe;
4. confirm the qualifying failure is cleared; and
5. only then mark the incident healthy/resolved.

If verification fails:

- record the failed recovery;
- do not immediately retry inside the same execution;
- apply cooldown/budget rules; and
- escalate when the policy says no further automatic attempt is safe.

No adapter contains hidden mutation retries.

## 18. Escalation

AI HQ must escalate rather than mutate further when any of the following is true:

- recovery budget exhausted;
- repeated post-recovery verification failure;
- storage unavailable or not writable;
- PostgreSQL is active but database health remains bad;
- Nginx is active but configuration/local probe remains unhealthy after one recovery attempt;
- Cloudflared is active but the evidence does not identify a process failure;
- unknown dependency is causing DripVid readiness failure;
- recovery configuration is invalid;
- scoped approval rule is unavailable/expired/exhausted; or
- Safety Service blocks the action.

Escalation must include a concise reason and bounded diagnostic evidence so the operator can act without reading a full journal dump.

## 19. Audit Requirements

For each automatic recovery incident, the audit trail must make it possible to reconstruct:

- what first failed;
- how many observations confirmed the failure;
- which component was selected;
- what health/status/log evidence was captured;
- which recovery policy matched;
- capability and permission result;
- Safety Service decision;
- scoped approval rule identifier, if used;
- whether execution was simulated or real;
- whether Host Helper performed a mutation;
- post-recovery verification result;
- cooldown/budget counters; and
- whether the incident ended healthy or escalated.

Do not duplicate ledger events already emitted by Tool Gateway/Safety/Approval. Add recovery-specific incident events only for information not already reconstructable.

## 20. DripVid Changes

DripVid itself should require only small additions for 2.90 because most observability already exists.

Expected DripVid-side work:

- preserve existing `/health/live`, `/health/ready`, and `/health` behavior;
- expose core-storage state in a bounded admin/operational diagnostic response if AI HQ cannot already obtain it safely;
- ensure readiness failures remain dependency-specific and structured;
- add any missing tests proving health responses fail closed when dependencies/storage required for the request flow are unavailable; and
- document 2.90 automatic-recovery behavior in the DripVid roadmap/release notes.

Do not duplicate the existing bug system, admin notifications, storage manager, or health probe implementation.

## 21. AI HQ Changes

Expected AI HQ-side work:

- recovery component configuration contracts;
- `service.recover` adapter and trusted transport operation;
- recovery incident persistence/service;
- periodic health observer;
- failure classifier/evaluator;
- cooldown and rolling-budget enforcement;
- scoped-rule-aware autonomous recovery mission creation;
- post-recovery verification;
- escalation/notification integration;
- recovery-specific audit coverage; and
- dashboard/API exposure only where required to show recovery state.

The existing `service.restart`, deployment, rollback, Safety Service, Approval Service, MissionExecutor, Tool Gateway, Host Helper, and ledger remain authoritative boundaries.

## 22. Testing Requirements

Automated tests must never restart production services.

Use fakes/test doubles for every mutating transport.

Required tests include:

- a single failure causes no mutation;
- three configured consecutive qualifying failures open recovery;
- healthy observation resets the consecutive-failure counter;
- unknown component fails closed;
- arbitrary service/unit/command/path parameters are impossible;
- recovery requires exact `service.recover` permission;
- ordinary `service.restart` still requires approval;
- recovery without matching scoped rule cannot mutate autonomously;
- matching BLUE scoped rule allows only the exact component/condition scope;
- FREEZE blocks recovery;
- SAFE blocks real recovery mutation;
- simulation causes zero transport mutation;
- storage failure never triggers service restart;
- app recovery executes only for qualifying app failure;
- MCP recovery executes only for inactive/failed MCP service;
- Nginx recovery executes only for qualifying proxy failure;
- Cloudflared recovery executes only for qualifying tunnel failure;
- PostgreSQL auto-recovery executes only when service status is inactive/failed;
- PostgreSQL active + failed DB query escalates without restart;
- one recovery attempt is followed by verification;
- failed verification does not hidden-retry;
- cooldown blocks immediate second recovery;
- rolling budget blocks the third recovery within 60 minutes under default policy;
- recovery counters persist across service reconstruction;
- two workers cannot claim the same recovery incident concurrently;
- exhausted budget escalates;
- invalid recovery configuration disables recovery fail-closed;
- ledger/recovery records reconstruct the incident without secrets;
- full existing AI HQ Stage 2 security tests remain green;
- full DripVid regression suite remains green.

## 23. Production Enablement Gate

Merging code does not automatically enable autonomous production recovery.

Production enablement sequence:

1. deploy code with automatic recovery disabled;
2. verify existing read-only health/status/log operations against production;
3. verify the trusted recovery component mapping;
4. run simulation-mode recovery scenarios and prove zero mutation;
5. create finite scoped approval rules for the exact DripVid recovery component conditions;
6. enable automatic recovery for selected components;
7. perform one explicitly observed real recovery test against a safe selected component;
8. verify audit trail, cooldown, budget, and post-recovery health; and
9. enable the remaining approved component policies.

The first real production mutation must be deliberate and observed.

## 24. Acceptance Criteria

DripVid 2.90 automatic recovery is complete only when:

- persistent qualifying failures can create an autonomous recovery incident;
- transient single failures do not mutate production;
- only trusted DripVid component keys can be recovered;
- agents cannot choose systemd units or commands;
- automatic recovery travels through MissionExecutor -> Tool Gateway -> Safety -> scoped approval -> restricted adapter -> Host Helper;
- normal manual restart/deploy/rollback approval behavior is unchanged;
- storage incidents never trigger blind service restarts;
- PostgreSQL active-but-unhealthy failures escalate instead of causing restart loops;
- each real recovery is followed by bounded health verification;
- cooldown and rolling budgets prevent restart loops;
- recovery protections persist across worker/process restarts;
- concurrent workers cannot duplicate a recovery mutation;
- simulation performs zero external mutation;
- recovery decisions/results are auditable;
- exhausted/unsafe incidents escalate cleanly;
- existing AI HQ security regression tests pass;
- existing DripVid tests pass; and
- production remains disabled until the explicit enablement gate is completed.

## 25. Explicit Non-Goals

DripVid 2.90 automatic recovery does not include:

- arbitrary shell access;
- unrestricted systemd management;
- arbitrary service discovery;
- automatic deployment or rollback;
- automatic database repair/schema changes;
- automatic storage mounting/repair;
- automatic router/firewall changes;
- package installation/upgrades;
- automatic media-file mutation in response to health failures;
- bypassing Safety Service or Tool Gateway;
- removing approval requirements from normal operational commands;
- infinite or immediate mutation retries; or
- a replacement for systemd's own basic restart-on-crash behavior.

## 26. Design Rationale

A separate `service.recover` capability is intentionally more constrained than reusing `service.restart`.

Reusing `service.restart` with a hidden approval exception would blur the distinction between an operator-requested restart and policy-driven recovery. It would also make future permission and audit reviews harder.

A dedicated recovery capability keeps the contract explicit:

- manual restart remains manual/approval-protected;
- automatic recovery is separately permissioned;
- automatic recovery requires a matching scoped rule;
- the component and failure conditions are policy inputs, not arbitrary operator commands;
- recovery-specific cooldowns, budgets, persistence, and verification are first-class; and
- the existing Stage 2 security boundary stays intact.
